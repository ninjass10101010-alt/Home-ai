# Kitchen Feature — Current Architecture (post-overhaul, August 2026)

## 1. Overview

The Kitchen feature spans 5 PocketBase collections with real calendar-week scheduling, recipe-as-reference resolution, auto grocery consolidation, and pantry-aware recipe suggestions. All state is PB-primary with in-memory cache + localStorage fallback via `CacheRefresher` (60s polling).

## 2. Data Model

### 2.1 PocketBase Collections

| Collection | Purpose | Key fields |
|---|---|---|
| `meal_plan_entries` | Weekly meal schedule | `name`, `emoji`, `time` (weekday), `mealType`, `weekOf` (ISO Monday), `date` (ISO), `recipeId`, `recipeSnapshotAt`, `protein/carbs/fat`, `ingredients` (json), `tags` (json) |
| `recipes` | Recipe catalog (source of truth) | `name`, `emoji`, `ingredients` (json), `instructions`, `protein/carbs/fat`, `favorite`, `difficulty`, `rating` |
| `pantry_items` | Pantry inventory with quantities | `item`, `status`, `category`, `quantity` (number), `unit` |
| `grocery_list_items` | Shopping list with deduped quantities | `name`, `category`, `aisle`, `quantity`, `quantityValue`, `unit`, `priority`, `needed`, `pinned`, `source`, `autoGenerated`, `manualOverride` |
| `meal_week_archive` | Archived weekly meal snapshots | `weekStart`, `archivedAt`, `data` (json) |

### 2.2 TypeScript Types

Single canonical source: `src/types/meals.ts`. Exports `Meal`, `Recipe`, `PantryItem`, `GroceryItem`, `Tab`.

### 2.3 Week Model

Mirrors the Tasks feature's `weekStart` pattern (`task-utils.ts`). Each meal has a `weekOf` (ISO Monday) and an optional `date` (ISO date). Week utilities: `src/lib/meals-week-utils.ts`.

## 3. Recipe Model — Reference, Not Snapshot

- Meals store `recipeId` + `recipeSnapshotAt` instead of copying all recipe fields permanently.
- At render time, `resolveMealEntry()` in `MealsTab.tsx` checks if the catalog recipe has been updated since the snapshot — if so, the meal displays the live recipe data.
- When a catalog recipe is edited (`useRecipes.saveCatalogRecipe`), all linked meals are updated in PB with fresh fields.
- New meals created from recipes (`addRecipeToPlan`, `addRecipeToMealSlot`) store `recipeId` and `recipeSnapshotAt`.

## 4. Scheduling — Real Calendar Weeks

- `useMeals` tracks `activeWeek` (ISO Monday) and `activeDay` (weekday short).
- Week nav: `goToWeek(delta)` shifts by ±1 weeks, defaults to Monday.
- Archive: `archiveCurrentWeek()` stores the week's meals into `meal_week_archive` and deletes them from the planner.
- Restore: `/meals/archive` route lists archived weeks with a "Restore" button that re-creates `meal_plan_entries` rows.
- Meal creation sets `weekOf = activeWeek`. Copy/duplicate scoped to current week.

## 5. Auto Grocery Sync

- `mealSyncService.syncMealPlanToGrocery()` accumulates ingredient deficits across all planned meals, dedupes by normalized name, sums quantities, and creates/updates grocery items.
- Deficit math: `calculateDeficit()` compares recipe quantity against pantry `quantity` (real math), falling back to `status`-based logic for legacy data.
- Sync writes directly to PB (no in-memory-only mutations).
- Manual override: `pinned` field on grocery items skips them during sync. `source === 'manual'` also skips.
- Sync is triggered manually via "🔄 Sync to Grocery" button in `MealsTab`.

## 6. Pantry-Aware Recipes

- `src/lib/recipe-pantry-match.ts`: `findCookableRecipes()` sorts catalog recipes by ingredient readiness (% of ingredients found in pantry).
- Ingredient matching normalizes names, strips stop words, handles substring matches.
- Ready for UI integration via `CookWithWhatYouHave` component.

## 7. Recipe Import

- `POST /api/recipes/ingest`: accepts `{ type: "url", url, sourceLabel }` or `{ type: "text", fileText }`.
- Fetches URL via `fetch()`, extracts text using `@mozilla/readability` + `linkedom` (no headless browser).
- Prefers Schema.org Recipe JSON (`<script type="application/ld+json">`) before falling back to Readability.
- Blocks private/localhost/loopback IPs via `isPrivateIP()`.
- Sends extracted text to Hermes LLM for structured parsing.
- No Playwright dependency.

## 8. Sync-Cache Architecture (fixed)

- `db.selectMeals()`, `db.selectPantry()`, `db.selectGrocery()` are **async** passthroughs to `pbDb.*` (was synchronous cache-read, causing race conditions on fresh load).
- `db.pantryStore` / `db.mealsStore` / `db.groceryStore` provide synchronous cache access for `useMemo` callers (e.g., `ingredientReadiness`).
- Hook init effects use `.then()` pattern (mirrored from `useRecipes.ts`).
- `CacheRefresher` polls PB every 60s + on visibility change, mutates in-memory caches.

## 9. Seed System

- `pb:seed`: runs `tsx scripts/pb-seed.mjs` which imports `seedCollections` from `src/lib/pb-seed.ts` (single source of truth).
- `seedCollections` is idempotent — patches missing schema fields on existing collections, creates new ones.
- No duplicate `COLLECTIONS` definitions. No hardcoded credentials.

## 10. Design Decisions

- **Meals/grocery/pantry are family-scoped** — same data for every logged-in user. No per-user isolation needed.
- **`pb-auth.ts` requires env vars** — `PB_ADMIN_EMAIL` and `PB_ADMIN_PASS` with no fallback.
- **Dead routes removed** — `/api/meals` and `/api/sync` deleted.
- **`services/types.ts` deleted** — types consolidated into `src/types/meals.ts`.
